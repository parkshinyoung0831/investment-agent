### [EX2-01] 승인 시점 planner와 실행 시점 planner가 다른 한도를 써서, 재검증이 영구히 "재승인 필요"로 막힌다  [확정] [높음] [정확성·구조]
- 파일:
  - src/investment_agent/operations/commands/request_toss_approval.py:474-488 (`_whole_share_planner`)
  - src/investment_agent/execution/orders/live_worker.py:337-342 (worker 기본 planner)
  - src/investment_agent/operations/commands/execute_toss_live.py:65-70 (`planner=` 를 넘기지 않음)
  - src/investment_agent/execution/orders/planning.py:172-198 (min/total 한도가 계획 결과를 바꾼다)
- 증상: 승인 카드를 정상적으로 받아 눌러도 `execute_toss_live`가 항상
  `Toss holdings, cash, or prices changed the approved order quantities; reapproval required`
  (또는 `total order notional ... exceeds ...`)로 멈춘다. 계좌도 시세도 안 바뀌었는데 그렇다.
- 근거: 승인 경로의 planner는
    `min_order_notional=TOSS_MIN_ORDER_NOTIONAL_USD`, `max_total_notional=TOSS_MAX_TOTAL_NOTIONAL_USD`
  를 읽고, worker의 기본 planner는
    `min_order_notional=10.0`(하드코딩), `max_total_notional=controls.max_daily_notional_usd`(=`TOSS_MAX_DAILY_NOTIONAL_USD`)
  를 쓴다. `execute_toss_live.main`은 `worker_factory(repository=..., api=..., controls=..., durable_control=...)`
  로만 부르므로 worker가 자기 기본 planner를 만든다 — 두 경로가 같은 planner를 공유하는 코드가 없다.
  `revalidate_live_handoff`(live_worker.py:276-290)는 worker planner로 다시 계획해
  `(client_order_id, symbol, side, quantity)` 튜플을 승인 주문표와 **완전 일치**로 비교한다.
- 재현(구체 숫자): `.env.example`에 있는 `TOSS_MIN_ORDER_NOTIONAL_USD`를 10 → 50으로 올린다.
  $20짜리 리밸런싱 주문 1건 + $600 주문 2건인 계획이면 승인 카드에는 2건이 실리고(planning.py:172 `continue`),
  worker 재검증은 min=10.0이라 3건을 만든다 → `fresh_identity`(3튜플) != `approved_identity`(2튜플) → 예외.
  같은 방식으로 `TOSS_MAX_TOTAL_NOTIONAL_USD=30000`, `TOSS_MAX_DAILY_NOTIONAL_USD=20000`이면
  합계 $25,000 계획이 승인은 통과하고 재검증에서 `total order notional 25000.00 exceeds 20000.00`으로 죽는다.
- 원인: 같은 "계획 규칙"을 두 진입점이 각자 조립한다. 한쪽은 env 3개, 한쪽은 하드코딩 1개 + controls 2개.
  `docs/ENV.md:88`은 `TOSS_MAX_DAILY_NOTIONAL_USD`만 문서화하고 `TOSS_MIN_ORDER_NOTIONAL_USD`·
  `TOSS_MAX_TOTAL_NOTIONAL_USD`는 `.env.example:84,86`에만 있어, 운영자가 어느 쪽을 바꿔야 하는지 알 수 없다.
- 해결: planner 조립을 함수 하나(예: `planning.whole_share_planner(config)`)로 모으고 승인·실행이 그것을 쓴다.
  `TOSS_MAX_TOTAL_NOTIONAL_USD`와 `TOSS_MAX_DAILY_NOTIONAL_USD`가 같은 것을 주장하므로 하나로 줄인다.
  가드: 두 진입점의 `ExecutionLimits`가 같은 값을 내는지 비교하는 테스트(현재 없음 — 각 경로만 따로 검증한다).
- 위험: fail-closed(승인 소비 전에 멈춘다)라 돈은 새지 않는다. 대신 실주문 경로가 조용히 **영구 불능**이 되고
  오류 문구가 "계좌·시세가 바뀌었다"로 원인을 가린다.

### [EX2-02] 30초 risk state 창이 준비 단계(네트워크 8~10회)에 소진돼, 승인을 소비한 뒤 배치가 첫·둘째 주문에서 잘린다  [확정] [높음] [정확성] [사용자결정]
- 파일:
  - src/investment_agent/execution/orders/live_worker.py:425 (`current = parse_datetime(now or self.clock())`)
  - src/investment_agent/execution/orders/live_worker.py:471-476 (`runtime_risk_state(..., captured_at=current)`)
  - src/investment_agent/execution/safety/control.py:40,285-288 (`MAX_STATE_AGE_SECONDS = 30`, `state_age > max` → 예외)
- 증상: 승인은 소비되고(`consumed`) 첫 주문 몇 건만 나간 뒤
  `runtime risk state is stale`로 intent가 `failed`가 된다. 이미 나간 주문은 브로커에 살아 있고,
  나머지는 `failed`로 닫힌다. 같은 승인을 다시 쓸 수 없어 부분 실행 상태에서 사람이 개입해야 한다.
- 근거: `captured_at`이 `execute()` **시작 시각**이다. 그 시각 이후 제출 전까지 아래가 순서대로 일어난다.
  1. `assert_official_us_session` → `toss_read.fetch_us_regular_session` (HTTP)
  2. `unresolved_orders` (sqlite), `current_tracked_tickers` → Supabase `universe.securities` 전체 페이징
  3. `snapshot_provider` = `toss_manual.build_snapshot` → `fetch_open_orders`·`fetch_holdings`·`fetch_prices`·
     `fetch_buying_power` (HTTP 4회, toss_manual.py:328-376)
  4. `_preflight_broker` → 매도 종목당 `sellable_quantity` + `commissions` + `buying_power` (HTTP 3회 이상)
  5. 주문마다 `create_planned_order` → `db.py:249-260 _with_security_identity`가 **주문 1건당 Supabase
     `universe.securities` 조회 1회**(메모리 기록: `sb.schema()` 왕복 약 0.4초)
  즉 주문 N건이면 Supabase 왕복 N+1회 + 토스 HTTP 8회 이상이 30초 예산 안에서 먼저 소비된다.
  제출 루프는 `submit_time = parse_datetime(self.clock())`로 실제 시각을 다시 읽으므로(live_worker.py:579)
  준비 시간이 그대로 `state_age`에 들어간다.
- 재현(구체 숫자): 주문 8건, Supabase 왕복 0.4초 × 9 = 3.6초, 토스 HTTP 8회 × 0.3초 = 2.4초,
  세션·스냅샷 검증 포함 준비에 8~15초. 남는 것이 15~22초이고 POST 1건당 0.3~1초 + `load_intent`·
  `load_control_state`(sqlite) 2회가 붙는다. 앞 주문 하나가 느리거나 토스가 3초 걸리면 뒤쪽이 창을 넘는다.
- 원인: 창의 **시작점**이 잘못됐다. `MAX_STATE_AGE_SECONDS`는 "위험 상태가 얼마나 낡았나"를 재는 값인데,
  지금은 "실행 시작부터 얼마나 지났나"를 잰다. 직전 보고서 TE-9는 `captured_at`을 주문마다
  갱신하지 않도록 고쳤고(그 자체는 옳다), 그 결과 창이 준비 단계까지 덮게 됐다.
- 테스트가 결함을 가린다: `tests/investment_agent/execution/test_live_worker.py`는 23곳에서 `now=NOW`를
  넘긴다. `now is not None`이면 `submit_time = current`로 고정되어 `state_age`가 항상 0이다.
  가짜 시계를 쓰는 두 테스트(:501, :521)도 준비 단계에 시간을 **흐르게 하지 않는다** —
  `clock()` 호출은 시작 1회 + 제출 N회뿐이라 준비 비용이 0으로 모델링된다.
- 해결(사용자 결정): risk state를 제출 루프 **직전에** 캡처하고(준비가 끝난 시점의 시계로) 30초를
  제출 구간에만 적용한다. 또는 `create_planned_order`의 종목 identity 조회를 배치 1회로 바꿔
  준비 비용을 줄인다(정확성 변경 없음, 이쪽은 결정 불필요). 창 길이를 늘리는 것은 위험 판정이
  낡은 상태로 열리는 쪽이라 값 변경은 사용자 결정.
- 위험: 승인 소비 후 부분 실행. 목표 비중이 중간 상태로 남고, `unresolved_orders`가 남아 다음 실행도 막힌다.

### [EX2-03] 브로커가 REPLACED를 주면 대사 전체가 예외로 끊기고, 남은 주문은 영구히 미해결로 남는다  [확정] [높음] [정확성]
- 파일:
  - src/investment_agent/execution/reconciliation/worker.py:75-76 (`classify_remote_order` → `"replaced"`)
  - src/investment_agent/execution/orders/repository.py:227-241 (`update_order_execution`의 전이표)
  - src/investment_agent/execution/orders/repository.py:261 (`reconcilable_orders`는 `'replaced'`를 안다)
  - src/investment_agent/execution/reconciliation/worker.py:336 (intent 판정도 `'replaced'`를 안다)
- 증상: 토스 주문 상태 문자열에 `REPLAC`가 들어오면(정정 주문의 원 주문 등)
  `ExecutionSafetyError: invalid order execution transition`이 `run_once` 밖으로 튀어
  **그 패스의 나머지 주문 전부가 대사되지 않는다**. `unresolved_orders`가 비지 않으므로
  `live_worker.execute`는 이후 모든 실주문을 `... await reconciliation; new orders are blocked`로 막는다.
- 근거: 전이표에 `replaced`가 **목표로도, 출발 상태로도 없다**.
  `transitions = {"planned": {...}, "submitted": {"partially_filled","filled","cancelled","rejected","outcome_unknown","reconciling"}, ...}`
  이고 `terminal = {"filled","cancelled","rejected","failed"}`다. 그런데 같은 저장소의
  `reconcilable_orders`는 `status IN ('filled','cancelled','rejected','replaced')`로 `replaced`를 다루고,
  대사 worker의 intent 판정은 `statuses & {"cancelled","rejected","failed","replaced"}`를 본다.
  즉 세 곳이 `replaced`를 아는데 **쓰는 곳 하나만 모른다**.
- 재현: `TossOrderSnapshot.status = "REPLACED"`, `filled_quantity=0`, 로컬 상태 `submitted`
  → `classify_remote_order` = `"replaced"` → `update_order_execution(status="replaced")`
  → `"replaced" not in transitions["submitted"]` → raise. `run_once`의 `for row in local` 안이라
  예외가 그대로 올라간다(주문별 격리 없음).
- 원인: 상태 enum이 한 모듈(전이표)에 선언되지 않고 세 곳에 흩어져 있다. `orders.status`에는
  DB CHECK도 없어(`db/sqlite/runtime/v1/30_execution.sql`의 `status TEXT NOT NULL`) 오타·누락이 DB에서도 안 드러난다.
- 해결: 주문 상태 enum과 전이표를 한 모듈 상수로 두고(`replaced`는 종결 상태로 추가),
  `classify_remote_order`의 반환 집합과 전이표의 목표 집합이 같은지 검증하는 테스트를 둔다.
  더불어 `run_once`의 주문 루프를 주문별로 격리해 한 건의 실패가 나머지 대사를 막지 않게 한다.
- 위험: 실주문 경로가 통째로 정지한다. 브로커에는 주문이 살아 있는데 원장이 상태를 못 옮긴다.

### [EX2-04] `order_attempts.state`가 한 번도 갱신되지 않아, System 목표 재실행 가드의 SQL 조건이 공허하다  [확정] [중간] [정확성·구조]
- 파일:
  - src/investment_agent/execution/orders/repository.py:132 (`INSERT ... state` = `"reserved"` 고정)
  - src/investment_agent/execution/orders/repository.py:35 (`o.state != 'failed'`)
  - db/sqlite/runtime/v1/30_execution.sql:59 (`CHECK (state IN ('reserved','submitted','unknown','failed'))`)
- 증상: 한 System 목표로 낸 배치가 **전부 실패**한 뒤에도 같은 목표로 새 intent를 저장할 수 없다
  (`ExecutionSafetyError: System target already has an active execution`). 자금 확보 매도
  예외(`funding_followup_allowed`)에 해당하지 않으면 그 목표는 영구히 막힌다.
- 근거: `state` 컬럼에 UPDATE가 저장소 전체에 **0건**이다(`grep "SET state"`·`"order_attempts SET"` 무결과).
  attempt의 실제 진행은 `order_events`가 갖고, `state`는 삽입 시각의 `'reserved'`로 굳는다.
  그래서 `EXISTS(SELECT 1 FROM order_attempts o WHERE o.intent_id=i.intent_id AND o.state != 'failed')`는
  "attempt 행이 하나라도 있으면 참"과 같다 — `!= 'failed'` 조건이 아무것도 걸러내지 않는다.
- 재현: 실패한 실행의 intent에 attempt 2건(둘 다 event가 `failed`)이 있는 상태에서
  같은 `system_target_id`로 `save_intent`를 부르면 `previous[3]`이 True → 예외.
  `state` 컬럼을 `'failed'`로 갱신하는 코드가 없어 어떤 경로로도 풀리지 않는다.
- 원인: attempt 상태가 두 곳(컬럼 + 이벤트 원장)에 있고, 실제로는 이벤트 원장만 갱신된다.
  검사 대상을 옮기면 검사가 조용히 통과/차단하는 패턴(직전 보고서의 "가드의 공허한 통과"와 같은 종류).
- 해결: 둘 중 하나로 통일한다 — (a) `state` 컬럼을 지우고 가드를 `order_events`의 마지막
  event_type으로 판정, 또는 (b) terminal 이벤트를 쓸 때 `state`도 같이 갱신. (a)가 진실을 하나로 만든다.
  가드 테스트는 "모든 attempt가 실패한 intent는 재실행을 막지 않는다"를 직접 물어야 한다.
- 위험: fail-closed(막는 쪽)이므로 중복 주문은 나지 않는다. 대신 실패 뒤 복구가 코드 수정 없이는 불가능하다.

  baseline 조회가 `performance_snapshot`도 함께 읽게 한다). 가드: 컷오프보다 오래된 fallback을
  요구하는 테스트(현재 없음 — 삭제 쪽과 조회 쪽 테스트가 서로를 모른다).
- 위험: fail-closed. 다만 실주문이 "왜 막혔는지" 메시지가 "장전 스냅샷을 찍어라"라서 원인(보관 삭제)을 가린다.

### [EX2-15] `LifecyclePromotionGate`의 최대낙폭 비교가 부호를 거꾸로 봐서 어떤 낙폭도 위반이 되지 않는다  [확정] [낮음(현재 죽은 코드)] [정확성]
