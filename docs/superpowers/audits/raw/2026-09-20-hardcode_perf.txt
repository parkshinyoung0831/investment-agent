# 하드코딩(HC) · 성능(PB) 감사 — 저장소 전체 (읽기 전용)

작성 기준일 2026-09-21. 직전 감사(`2026-09-20-silent-wrong-audit.md`)와 `2026-09-20-code-quality-overhaul.md`에 있는 항목은 세지 않았다.

## 0. 방법

- src 720개 파일을 AST로 훑었다: (a) for/while/컴프리헨션 안의 `.execute/.upsert/.rpc/select_*` 호출과, 그것을 한 단계 감싼 함수 호출(137곳 후보), (b) 함수 안 비교식의 숫자 리터럴, (c) 모듈 상수의 이름·값 중복, (d) URL·경로·날짜·CIK·ticker 리터럴, (e) `os.environ.get` 이름 83개와 `docs/ENV.md` 대조.
- 후보 중 **읽어서 끝까지 따라간 것만** "확정"으로 적었다. 나머지는 "의심".
- 측정은 네트워크 쓰기 없이 했다: 운영 DB는 SELECT만(PostgREST 조회·psycopg2 readonly), DuckDB는 운영 파일을 **임시 폴더로 복사한 사본**에서, Playwright는 로컬 Chromium. 운영 DB·파일에 쓴 것은 없다.
- 이 머신의 왕복(RTT): psycopg2 직결 `SELECT 1` ≈ 10ms, PostgREST 단건 조회 ≈ 30~230ms(쿼리에 따라).

## 2. 하드코딩 (HC)

### HC-1 KR 기준금리 공식 일정이 2026-11-26에서 끝난다 — "degraded 보고"는 주석뿐
- **영역**: `data/macro/domain/releases/schedule.py:22-29, 140-144`, 호출 `data/macro/application/release_calendar.py:59-60`
- **증상**: `_KR_BASE_RATE_DATES`는 2026년 8개 날짜뿐. 주석은 "매년 official calendar 갱신이 없으면 해당 family는 degraded로 보고한다"고 하지만 `degraded`를 내는 코드는 macro 전체에 없다(grep 0건). 창(window)이 목록 밖이면 `[]`를 돌려주고 호출부는 그대로 성공 처리한다.
- **재현**: `official_calendar_dates("KR_BASE_RATE", start=date(2027,1,1), end=date(2027,12,31))` → `[]` (예외·경고 없음).
- **원인**: 코드에 날짜를 전사하고, 만료를 검사하는 계약은 주석에만 있다.
- **고치는 방법**: (1) 창의 끝이 목록의 마지막 날짜를 넘으면 `ScheduleContractError`(=`failures`에 실려 운영 알림)로 올린다. (2) 날짜 자체는 `data/macro/releases/` 옆 JSON catalog(이미 `series_config.json`·`catalog_metadata.json`이 있다)로 옮겨 코드 리뷰 없이 갱신하고 만료 검사 테스트를 둔다. 새 config 디렉터리는 만들지 않는다.
- **위험**: 낮음. 만료 시점(2026-11-26 이후) 전에 넣어야 의미가 있다.
- **확정**, 난이도 낮음, 사용자 결정 불필요(단 2027 일정 전사는 사람이 공식 달력 확인).

### HC-2 시장 regime 임계값이 반쪽만 선언되고, 분산 임계는 척도가 안 맞는다
- **근거**: `trading/decision/regime.py:118-138, 156-163`(인라인 값), `:19-45`(`RegimeThresholds`), 입력 `reporting/services/investment/market_regime.py:43,55`
- **증상**:
  1. 유동성 `<0.20 stressed`·`<0.45 thin`·`>=0.75 deep`, macro `±0.25`, 분산 `>0.75`(신뢰도 ×0.9)는 `RegimeThresholds`에 없다. `metadata["thresholds"]=limits.to_dict()`와 `version="native-regime-v1"`에도 안 실려, 인라인 값을 바꿔도 같은 version으로 다른 판단이 기록된다.
  2. `dispersion`은 유일한 호출부(market_regime.py)에서 `pd.Series([SPY 21일수익, QQQ 21일수익]).std(ddof=0)`이다. 두 수익률 표준편차가 0.75를 넘으려면 두 종목 21일 수익 차이가 150%p여야 한다 — `dispersion_warning`과 신뢰도 감쇠가 **사실상 영원히 꺼져 있다**.
- **원인**: 0~1 클램프 값이라는 이유로 "비율 척도" 임계를 그대로 붙였고, 입력은 수익률 표준편차라 척도가 다르다.
- **고치는 방법**: 모든 임계를 `RegimeThresholds`로 옮기고(version 올림), 분산은 입력의 척도(예: 수익률 std 0.05~0.10)에 맞춘 값으로 정하거나, 정의를 "0~1 정규화 분산"으로 통일해 입력 쪽에서 정규화한다. hard risk limit(`gate.py`)은 건드리지 않는다.
- **위험**: regime 상태가 바뀌어 `regime_budget`(배율은 임시값이라 메모리에 기록됨)에 파급. 값 변경은 사용자 승인 원칙 영역일 수 있다.
- **확정**(코드 경로 확인, 분산 척도는 산식으로 증명), 난이도 낮음, **사용자 결정 필요**(임계 값 자체·version 올림 시 재계산 여부).

### HC-3 토스 보유 동기화가 해제 시각을 매번 덮어쓰고 변경 없는 행도 전부 쓴다
- **근거**: `data/universe/watchlists/db.py:sync_toss_members` (`for row in members:` 루프, `removed_at=None if sources else datetime.now(...)`), `data/universe/repository.py:408-425`
- **재현**(가짜 저장소, 실행 결과):
  ```
  입력 members: AAA(toss) / BBB(이미 해제, removed_at=2026-03-01) / CCC(manual)
  결과: unchanged=3, upsert 3회. BBB의 removed_at → 2026-09-20T15:46:11 (덮어씀)
  ```
- **원인**: 모든 멤버를 `sources`로 다시 계산해 UPDATE한다. 이미 빈 `sources`면 `removed_at`을 새로 찍는다. 컬럼 주석은 "마지막으로 관심에서 빠진 시각"이다.
- **운영 수치**: `universe.entities` 관심 활성 50, 해제 이력 0 → 아직 안 드러났다. 누군가 한 번 해제하면 그 회사의 이력이 다음 동기화부터 계속 움직인다. `unchanged`도 부풀려 보고된다(변경 없는 3건이 unchanged=3인 건 맞지만 "쓴 행"과 다르다).
- **고치는 방법**: 계산 결과가 현재 상태(`sources`·`removed_at`)와 같으면 쓰지 않는다. 해제 시각은 `sources`가 **비어 있지 않은 상태에서 빈 상태로 바뀔 때만** 찍는다. `date.today()`(watch_from)는 `_us_market_today`와 같은 달력으로 통일.
- **위험**: 낮음. 워치리스트 `watch_from`/제거 이력은 실적 카드 시즌 게이트가 읽을 수 있음.
- **확정**, 난이도 낮음, 사용자 결정 불필요.

## 3. 성능 (PB)

### PB-1 매일 도는 valuation 적재가 종목마다 단건 왕복 — 배치 경로가 historical에만 연결돼 있다
- **근거**: `research/commands/build_valuations.py:90-94`(`prepare_historical_replay`는 `source_kind == "historical_replay"`일 때만 호출), 루프 `:96-`에서 `fundamentals_pit`·`share_class_snapshots_pit`·`split_history`·`market_prices` 종목당 호출. 실행 경로: `operations/adapters/research.py:build_valuations`(기본 `live_shadow`, 종목 = tracked 503).
- **왕복 견적(종목당)**: 재무(증권→버전→공시) 3 + 발행주식수(증권ID→스냅샷→공시) 3 + 분할(ID→분할) 2 + 가격 2(로컬 mirror가 없거나 오래되면) ≈ **8~10회 × 503 ≈ 4,000~5,000회**.
- **실측**(운영 DB SELECT, 이 머신): 종목당 `fundamentals_filed_before` 228ms, `share_class_snapshots_filed_before` 100ms, `split_history` 33ms. 10종목 표본 재무+주식수 158ms/종목 → 503종목 **≈ 79초**. 같은 입력을 배치 함수(`securities_fundamentals_filed_before` 12.8초 + `share_class_snapshots_for_tickers_filed_before` 8.0초)로 읽으면 **≈ 21초**(재무 5,965행). 분할까지 배치하면 추가 ≈ 17초 절감. 즉 **하네스 1회당 ≈ 58~75초**, 그리고 왕복 수(~4,500→~40)가 서버·rate에 주는 부담이 준다.
- **원인**: `prepare_historical_replay`가 이미 fundamentals/shares/splits/consensus/segments를 날짜당 한 번에 읽어 단건 계약 캐시에 `seed`한다. 이 배치 경로가 live_shadow에는 안 붙었다. 주의: 그 함수는 consensus·segments까지 읽으므로 valuation만 필요한 live 경로엔 세 도메인(재무·주식수·분할)만 seed하는 좁은 버전이 맞다.
- **고치는 방법(하드코딩 없이)**: `prepare_pit_inputs(tickers, as_of, *, domains=(...))`로 분리하고 두 source_kind에서 호출. seed 키가 단건 계약과 같으므로 단건 API는 그대로. 동치성 테스트(배치 결과 == 단건 결과)를 둔다 — 테스트 픽스처가 리더보다 풍부하지 않게 실제 reader 계약(`limit`, 필터)으로 검증.
- **위험**: 낮음(읽기 전용). 단, 배치와 단건이 `is_active_listing` 필터·`limit` 자르는 위치가 다르면 값이 달라질 수 있어 위 동치 테스트가 필수.
- **확정**(실측), 난이도 낮음~중간, 사용자 결정 불필요.

### PB-2 Research DuckDB는 연결마다 DDL 전체를 다시 적용한다
- **근거**: `research/storage/repository.py:59-73` `_connect()` → `platform/db/duckdb.py:transactional_connection`이 **매번** `ddl_statements(dir)`를 읽고 10개 문장을 `execute`, 이어 `_migrate_legacy_*` 두 점검.
- **실측**(운영 `research.duckdb`를 임시 사본으로 복사해 측정, 8.4MB):
  | 단계 | 시간 |
  |---|---|
  | 파일 열고 닫기만 | 75ms |
  | + DDL 10문장 | 212ms |
  | 트랜잭션+DDL | 220ms |
  | `ResearchStore._connect`(마이그레이션 점검 포함) | **242ms** |
  | 실제 `upsert_allocation` 1건 | **255ms** (작은 빈 DB 66ms) |
  DDL 파싱 자체(`ddl_statements`)는 1.1ms — 비용은 **`CREATE TABLE IF NOT EXISTS`×10 실행**(≈140ms)과 마이그레이션 점검(≈20ms)이다.
- **호출 횟수 견적**: 저장 메서드가 행/묶음마다 `_connect()`를 부른다 — `strategies/etl.py:85,105,161` 백필은 (전략 수 × 개월 수)회 `upsert_allocation`(예: 8×60=480회 ≈ **2분**), `save_decision_experiences`·`save_evaluation`류 루프, `intelligence` 저장소도 같은 `duckdb_store`를 쓴다. 이 때문에 예전에 "종목마다 DuckDB를 열면 0.3초"(reader.py 주석)로 기술지표를 통째 읽게 우회했다.
- **고치는 방법**: DDL 적용을 **프로세스당·파일당 1회**로(모듈 레벨 `set[(resolved_path, ddl_hash)]`), 이후 연결은 DDL·마이그레이션 점검 생략. DDL 파일 mtime/해시가 바뀌면 다시 적용. 쓰기 루프에서는 `with store.batch():`로 연결 하나를 재사용하는 API도 고려.
- **위험**: 중간. DDL을 안 다시 적용하면 다른 프로세스가 스키마를 바꿨을 때 놓칠 수 있다(해시 키로 완화). 하네스가 여러 프로세스로 동시에 쓰는 구조(`_open_with_retry` 주석)라 트랜잭션 경계를 바꾸면 안 된다.
- **확정**(실측), 난이도 중간, 사용자 결정 불필요.

### PB-3 사후 평가가 케이스마다 SPY 경로와 ID 조회를 되풀이한다

HC-3과 같은 코드. `sync_toss_members`가 활성 50개를 전부 `_upsert_member`(=단건 UPDATE)하므로 동기화 1회 = 50~ 왕복(≈ 2~3초)이고 실제 변경은 보통 0~1건. HC-3의 "변경 없으면 쓰지 않는다"만 고쳐도 사라진다. 확정, 낮음.

### PB-5 삭제·갱신이 행 단위인 곳 (배치 가능)
- `data/fundamentals/infrastructure/supabase/segment_metrics.py:198-206` stale 세그먼트를 **행마다** DELETE(키 5개 eq). `share_class_snapshots.py:89-97` stale 스냅샷 행마다 DELETE. `company_financials.py:315-323` CIK마다 DELETE 1회(전체 재처리 때 CIK 수만큼, ≈503회), `data/universe/persistence.py:513-520`(`apply_toss_names` 이름별 UPDATE — PostgREST upsert는 NOT NULL 때문에 부분 컬럼 갱신이 안 돼 RPC가 필요, 메모리 참고), `data/macro/repository.py:135`(변경된 카탈로그 행별 UPDATE, 카탈로그 ≈ 30~100행).
- 각 항목의 빈도가 낮다(재처리·백필·카탈로그 변경 시). 정상 일일 경로에서 발생 횟수는 보통 0~수 회라 심각도 낮음. 배치 방법: 세그먼트는 `(cik, accession_no)` 단위로 `in_` 삭제 후 keep 재삽입(멱등), stale이 있는 accession 목록만 대상으로 한다. **확정(코드)**, 실제 횟수는 데이터 의존(측정 안 함).

### PB-6 정합성 점검의 count 9회 직렬
`fundamentals/infrastructure/supabase/integrity.py:108-115`: `FILL_FLOORS` 9개 컬럼마다 `select(count="exact").not_.is_(col,"null")` 1회. 실측 1회 0.87초 → **≈ 7.8초** + 파생 부채 1회. 표가 커지면 8초 statement_timeout에 각각 근접한다(현재 각 0.87초로 여유). 개선: 뷰/RPC 하나에서 `count(*) filter (where col is not null)` 9개를 한 번에(RPC는 DDL이 얽히므로 **사용자 결정 필요**). 확정, 낮음.

### PB-7 알림 카드마다 Chromium을 새로 띄운다
`notifications/playwright.py:capture_html_to_png`(호출마다 `async_playwright()`·`chromium.launch()`), 호출부 `earnings_report/run.py:141`(공시 알림 건마다 `asyncio.run`), `macro/core.py:168`, `earnings_calendar/run.py:92`.
- **실측**(로컬 Chromium, 단순 HTML): 1장 = 1.2초(콜드 3.4초), 브라우저 재사용 시 장당 0.65초 → **장당 ≈ 0.55초 절감**. 카드 수가 실적 시즌에 하루 최대 수십 장이면 절감은 ~10~30초 수준이고 브라우저 콜드 스타트는 Actions에서 더 크다.
- 부수: `browser.close()`가 try/finally가 아니라 캡처 예외 시 Chromium이 남는다(`playwright.py:45-63`), 임시 파일명 `abs(hash(html)) % 10**8`은 프로세스마다 다른 값(PYTHONHASHSEED)이라 재실행이 같은 파일을 덮어쓰지 못한다(기능 영향 없음, 임시 파일 누적).
- **고치는 방법**: 한 실행에서 여러 장이면 브라우저 하나로 `render_many(htmls)`. 규칙 15상 패키지별 `shoot_png` 래퍼는 유지하고 `capture_html_to_png`에 선택적 `browser=` 인자만 추가. 확정, 낮음.

### PB-8 알림 엔진의 notice별 원장 조회
`notifications/engine.py:140-142`(`replay`)·`:_without_unchanged`(`last_known` 1회/notice, `db.py:97`). 대상 topic이 `macro.alert`·`macro.daily`·`earnings.schedule`뿐이고 notice ≤ 수십이라 실제는 수십 왕복(수 초). reserve 자체는 100개씩 묶음(`RESERVE_CHUNK`)으로 이미 배치. 낮음. (`replay`는 사람이 부르는 `--force`에서만.)

### PB-9 뉴스·소셜 저장 (의심)
`intelligence/application/collect_news.py:85`, `collect_social.py:97`이 종목 루프 안에서 `store_news/store_mentions`를 호출하고 그 저장은 `_write_parquet`+DuckDB 연결을 열 가능성이 있다(`intelligence/repository.py:113,148,169,275,295`). 같은 `duckdb_store`를 쓰므로 PB-2와 같은 연결 비용이 종목마다 곱해질 수 있다. 저장 메서드 내부가 종목 하나당 연결을 여는지, 아니면 배치인지 **끝까지 확인하지 못했다**. 관심 종목(약 50개) × 240ms ≈ 12초 수준으로 추정. 의심, 낮음.
