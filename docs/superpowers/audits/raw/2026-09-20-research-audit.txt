## RS-5 [확정·높음(게이트 오작동)] RL 승격 게이트의 DSR이 단위가 어긋나 있다 — 기대 최대 샤프가 상수 1.11로 고정
- 영역: research/evaluation/deflated_sharpe.py:55-110, research/rl/continuous_learner.py:87
- 증상: `evaluate_model`이 `DeflatedSharpeRatio.compute(returns, num_trials=10, annualize=False)`로 **기간별(20일 구간) 샤프**를 넘기는데, `variance_trials`는 기본 0.5 상수라 `expected_max_sr = sqrt(0.5)·(…) = 1.1134`가 항상 같다. 기간별 샤프가 1.11을 넘어야 DSR≥0.5가 된다(연환산 시 약 3.9). 결과: 실제로 쓸 만한 정책도 `dsr_probability ≈ 0`, 반대로 기간별 샤프 1.3(비현실적) 이상이면 통과.
- 재현(순수 함수): 20일 기간 수익률 30개, σ=0.05, 평균 0.02/0.05/0.10 → 관측 SR 0.34/1.34/1.98, 기대최대 1.1134, DSR 확률 0.0/0.84/0.9993. 평균 0.02(기간 SR 0.34는 이미 매우 좋음)가 0.0.
- 추가 결함: `annualize=True`(기본) 경로는 SE 분산항(`var_sr`)에 **연환산 SR**과 (n-1)을 그대로 넣는다 — Mertens 식은 기간별 SR 기준이라 연환산 SE는 √ppy배여야 하는데 그대로라 표준오차가 ~13배 작다. 재현(일별 수익률 60개, σ=2%, ppy=252, num_trials=10): 평균 0.2%/일 → 구현 0.0728 vs 표준오차를 바로잡은 값 0.4532, 평균 0 → 0.0 vs 0.1646 (z가 과대 → 확률이 0/1로 쏠림). 현재 호출자는 `annualize=False`뿐이라 이 경로는 잠복.
- 로그에도 영향: `PolicyEvaluationScore.sharpe_ratio`가 "연율화 샤프비율"이라는 주석(:86)과 달리 기간별 값이고 `min_sharpe_improvement=0.02`가 그 단위에 걸려 있다.
- 원인: DSR 입력 단위(기간 SR)와 시도 간 SR 분산의 단위를 맞추지 않음. `variance_trials`는 시도들의 SR 추정치 분산(≈ 1/(n-1) 수준)이어야 함.
- 고치는 법: `variance_trials`를 인자 필수로 하고 호출자가 시도별 SR의 표본 분산(또는 1/(n-1))을 넘기게; annualize 경로의 SE는 기간 SR로 계산 후 √ppy 곱. 경계값 테스트(평균 0.02 케이스) 추가.
- 위험: RL은 challenger 전용이라 실주문 영향 없음. 게이트 통과 기준이 바뀌면 후보 채택 빈도가 바뀐다. 난이도 하. 사용자 결정: 승격 문턱 정책이라 확인 권장.

- 시스템이 이미 알고 있다: `artifacts/research/backfill_audit_2022_2025.json`의 날짜별 행이 `expected_count 505 / snapshot_count 425 / unavailable_count 80 / terminal_count 505 / coverage 1.0`(2022-01-07) — `unavailable`을 "끝난 것(terminal)"으로 세서 coverage가 1.0이 된다(`backfill.audit_backfill`의 `coverage = terminal/expected`). 원인이 '봉 없음'인지 다른 도메인 부재인지는 종목별로 재확인하지 않았다(`is_available=bool(sources)`, layer.py:344 — 근거 도메인이 하나도 없을 때만 미사용이므로 가격·재무·13F 모두 없다는 뜻; 봉 0개는 확인).
- 가드가 공허: `artifacts/research/data_quality_2022_2025.json`의 `feature_label_coverage: 1.0`, `label_sample_coverage: 1.0`은 snapshot↔label↔sample 간 비율이지 **멤버십 대비 커버리지가 아니다**. `EvaluationSummary.survivorship_incidents`를 세는 `survivorship_check_passed` 플래그는 생산자가 코드 어디에도 없다(RS-15).
- 영향: 인수·상장폐지·편출(대개 이후 수익률 분포가 다른 종목군)이 학습·factor IC(`factor_research`: 가중치 제안의 근거)에서 빠져 IC·spread가 낙관적. value factor는 특히 편출 부진주가 빠져 과대평가 가능.
- 고치는 법: (a) 최소: 재현 날짜마다 `snapshot_count / membership_count`를 `historical_replay_runs`와 데이터 품질 리포트에 기록하고 승격·채택 게이트(`check_adoptable`)에 최소 커버리지(예 95%)를 추가; (b) 근본: 과거 멤버의 봉을 backfill(market owner, yfinance로 상폐 종목이 안 받아지면 결측 비율을 그대로 공개).
- 위험: (b)는 외부 provider 호출·저장 증가, 이미 만든 96k 표본을 재생성(FEATURE_VERSION 승격). 난이도 (a) 하 / (b) 상. **사용자 결정 필요**.

## RS-15 [확정·중간] 모델 승격 게이트의 입력 `portfolio_evaluations` 데이터셋에 생산자가 없다 — 승격 경로가 구조적으로 닫혀 있다
- research/storage/repository.py:963-974 `model_evaluation_rows`가 `records("portfolio_evaluations")`을 읽고 `promote_model` 명령(operations/commands/promote_model.py)이 그 요약을 게이트에 넣는다. 그러나 src 전체에 `portfolio_evaluations`를 쓰는 코드가 없다(readers 4곳뿐, `data/local/research/parquet/datasets/`에 해당 디렉터리도 없음). `leakage_check_passed`·`survivorship_check_passed`·`data_integrity_check_passed`·`research_only` 필드도 생산자·DB 컬럼이 없다(test fixture에만 존재 → 테스트 픽스처가 프로덕션 리더보다 풍부).
- 결과: `aggregate_evaluations([])` → `evaluation_count=0`, `data_integrity_incidents=1`로 항상 "no persisted evaluation evidence" 위반. ManualPromotionGate/`has_approved_chain`(실주문 직전 검사)는 어떤 artifact도 통과시킬 수 없거나(fail-closed), 다른 곳에서 우회해 쓰이고 있다면 게이트의 의미가 없다. 
- 고치는 법: 생산자(walk-forward·paper 평가 → `portfolio_evaluations`)를 만들거나 게이트/명령을 삭제. fail-closed라 위험은 낮으나 "있는 것처럼 보이는 안전장치"다. 난이도 중. 사용자 결정 필요(실주문 승격 정책).

## RS-16 [확정·낮음] factor_research의 종가 캐시가 날짜만 키로 써서 다른 종목 집합의 조회를 가린다
- research/commands/factor_research.py `close_cache: dict[date, ...]`가 `closes(day, tickers)`의 tickers를 키에 안 넣는다. 주간 표본에서 horizon 20일의 end_day는 4주 뒤 as_of의 start_day와 같은데, 캐시는 먼저 요청한 날짜의 종목 집합으로 채워져 그 뒤 날짜에 새로 들어온 멤버는 시작가가 없어 조용히 수익률에서 빠진다(편입 종목이 IC 표본에서 누락).
- 고치는 법: 키에 `frozenset(tickers)` 대신 "전체 union을 한 번 조회". 난이도 하. 영향 작음(주간 멤버 변동 수 종목).

## RS-17 [의심·낮음] 후보 모델 4종을 같은 OOS 창에서 비교해 최고 ICIR을 추천 — 다중 비교 보정 없음
- research/commands/ml_challengers.py:beats_champion, `best = max(... icir)`. 4 종류 × 매 실행마다 새 후보를 만들고 champion보다 ICIR이 높으면 추천. `check_adoptable`은 후보 단독 IC t≥2만 보고 후보 수(deflation)를 반영하지 않는다. 채택은 사람이 하므로 위험은 낮으나 "추천"이 선택 편향을 담는다. 고치는 법: 후보 수를 OOS t-stat 임계에 반영(Bonferroni/DSR-IC), OOS를 선택과 독립된 마지막 구간으로 분리. 난이도 중.
