## WF-01 econ_calendar_watch의 `*/15 12-15` 스케줄이 사실상 안 돈다 (확정, 실측)
- 영역: .github/workflows/econ_calendar_watch.yml:17, notify_econ_calendar_release.yml:11-14
- 증상: 설계는 평일 하루 16회(발표 직후 8:30 ET = 12:30 UTC 포착). 실측은 08-21~09-20 한 달간 schedule 실행 **17회**(설계상 약 350회), 그것도 대부분 하루 1~2번, 시각은 15:24~19:05 UTC. 즉 12:30 UTC 발표 속보가 3~6시간 늦게 나간다. 파일 머리주석이 "발표 직후를 잡는 watcher"라 약속한 기능이 실제로는 안 된다.
- 근거: runs.json의 econ_calendar_watch 목록(9/14 17:12, 9/15 15:52, 9/16 15:44·19:05 ...). notify_econ_calendar_release도 cron 03:20/09:20/15:20/21:20 UTC인데 실제 생성 시각은 08:09/13:38/18:38/23:18 UTC 부근(2~5시간 지연). market_daily도 cron 23:30 UTC가 실제 01:12~01:38 UTC(+1.7~2h).
- 원인: GitHub Actions schedule은 고빈도 cron·정시 근처 혼잡에서 큐잉/드롭된다(공식 보장 없음). 코드는 "정시에 돈다"를 전제로 시각을 가정한다(예: watchlist_fast 21:30 UTC가 earnings_watch 22:00 UTC 직전).
- 고치는 법: 속보 경로는 Actions cron에 기대지 않는다. (a) 로컬 하네스가 이미 같은 `watch_releases` entrypoint를 부를 수 있다고 주석에 적혀 있으므로 하네스 job으로 1~5분 주기 등록하고 Actions는 안전망으로만 유지, 또는 (b) cron을 정각·15분 배수(`*/15`)가 아닌 비정렬 분(`7,22,37,52`)으로 옮겨 드롭률을 줄인다. 어느 쪽이든 하드코딩 신설 없이 워크플로/하네스 등록만 바뀐다.
- 위험: 낮음(알림 지연만). 알림 재발송 위험은 outbox가 막는다.
- 난이도: 하네스 등록이면 중간, cron 분 옮기기면 낮음. 사용자 결정 필요: 로컬 하네스 job으로 옮길지(고정 IP 머신 상시 가동 전제).

## OP-02 job 정의에 stage가 추가되면, 기존 waiting/paused 실행이 있는 하네스가 tick마다 KeyError로 죽는다 (확정, 순수 함수 재현)
- 영역: src/investment_agent/operations/harness/runtime.py:104-111 (`_next_stage`), :117-, service.py:run_forever `except Exception -> return 1`
- 재현: stage [a]인 job이 waiting인 state.json을 저장 → stage [a,b]로 정의를 바꿔 새 스케줄러로 `tick()` → `KeyError: 'b'`(실제 재현 완료). `_new_job`만 현재 정의로 stage 표를 만들고, 이미 저장된 active job의 `job.stages`에는 새 stage가 없다.

## OP-04 `HarnessService`의 heartbeat 스레드가 모든 active job의 heartbeat를 갱신해 stale 판정이 무력화된다 (확정, 코드 경로) + 스레드 경합 (의심)
- 영역: src/investment_agent/operations/harness/runtime.py:170-178 (`update_process_heartbeat`), service.py:59-66, health.py:48-53
- 증상: heartbeat 스레드(5초)가 `for job in state.jobs.values(): if job.active: job.heartbeat_at = now`를 한다. `inspect_health`의 `stale_jobs`는 `job.heartbeat_at` 오래됨을 본다 → 핸들러가 멈춰 있어도(프로세스는 살아 있음) job heartbeat가 계속 갱신돼 stale이 절대 안 된다. 잡별 `stale_after_seconds`(예: reconcile 5분, feature_store 30시간) 설정이 사실상 죽은 코드다. 레지스트리에서 사라진 orphan job(`investment_pipeline`)도 같은 이유로 stale이 되지 않고 `paused_jobs`에 영원히 남는다.

- 고치는 법: process heartbeat는 프로세스 필드에만 쓰고 job heartbeat는 tick/stage 진행에서만 갱신. state 접근을 `threading.Lock`으로 감싸기.
