### [OP2-01] waiting으로 폴링하는 stage가 attempts를 태워, 첫 실제 오류가 곧바로 terminal 실패가 된다  [확정] [높음] [정확성]
- 파일: src/investment_agent/operations/harness/runtime.py:246-247, 284-288 / harness/background.py:20-21 /
  adapters/execution.py:97-100
- 증상: `max_attempts=2~3`으로 선언한 stage가 실제로는 재시도를 한 번도 하지 않는다. 오류 하나로 job이
  `failed`로 굳고 `retry_delay_seconds`(10분·30초)는 영원히 쓰이지 않는다.
- 근거: `_advance`는 stage에 진입할 때마다 무조건 카운터를 올린다.
  ```python
  runtime.status = "running"
  runtime.attempts += 1
  ```
  `waiting`으로 돌아온 stage도 `resume_at`이 지나면 같은 자리로 다시 들어오므로 attempts가 계속 오른다.
  실패 판정은 오직 예외 경로에서만 비교한다.
  ```python
  if runtime.attempts >= stage_def.max_attempts:
      runtime.status = "failed"
  ```
  attempts를 초기화하는 곳은 코드 전체에 없다(`grep -n "attempts" runtime.py state.py` → 증가·검증뿐).
- 재현(구체):
  1) `approval_worker`(max_attempts=3, pipeline.py:73-79)는 승인이 `pending`인 동안 15초마다
     `StageOutcome.waiting`을 돌려준다(adapters/execution.py:93-100). TTL 15분이면 약 60회 → attempts≈60.
  2) 사람이 승인을 누르면 같은 stage가 `execute_toss_live` subprocess를 부른다. 이때 일시적 오류
     (토스 401·타임아웃) 하나가 나면 `60 >= 3`이라 **즉시 terminal**. 30초 뒤 재시도는 없고 job이 failed.
  3) background로 감싼 stage(`build_features` 등 13개)는 5초마다 waiting을 돌려준다
     (background.py:21 `resume_after_seconds=5`) → 2시간 실행이면 attempts≈1440. 그 뒤 실패는 무조건 terminal.
- 원인: attempts가 "handler를 실제로 실행한 횟수"가 아니라 "stage에 진입한 횟수"를 센다. waiting은
  실행이 아니라 대기인데 같은 카운터를 공유한다.
- 해결: waiting 복귀에서는 attempts를 올리지 않는다(예: `waiting`→`pending` 전이 때 플래그를 남기고
  handler가 예외로 끝난 회차만 센다). 또는 `StageRuntime.failures`를 따로 두고 max_attempts와 비교한다.
  가드: waiting을 N회 반복한 뒤 예외를 1회 내는 handler로 "재시도가 남아 있어야 한다"를 검증.
- 위험: 낮음(카운터 의미만 좁힌다). 다만 실주문 경로 코드라 정비 보류 하에서만.

### [OP2-02] background 단계가 6개 worker를 13개 stage와 공유하고 대기에 시간 상한이 없다  [확정] [중간] [정확성]
- 파일: src/investment_agent/operations/harness/background.py:10-23, harness_adapters.py:162-168
- 증상: 동시에 대기 중인 background stage가 6개를 넘으면 7번째는 **submit만 되고 시작되지 않는다**.
  그 stage는 5초마다 `waiting(reason=background_work_running)`을 영구히 돌려주고, heartbeat는 계속
  갱신되므로(`update_process_heartbeat`가 active job 전부를 갱신) health는 `healthy=True`다.
- 근거:
  ```python
  self.executor=ThreadPoolExecutor(max_workers=6,thread_name_prefix='investment-analysis')
  ...
  if not future.done():
      return StageOutcome.waiting(resume_after_seconds=5,metadata={'reason':'background_work_running'})
  ```
  감싸는 이름은 13개(harness_adapters.py:165-167). subprocess 타임아웃은 `command_runner.run` 안에서만
  동작하므로 **큐에 갇혀 시작되지 않은 future에는 어떤 타임아웃도 적용되지 않는다.**
- 재현: feature_store(6 stage는 순차라 1개)·investment_analysis·investment_reporting(2)·system_portfolio·
  decision_experience·continuous_learning이 겹치는 자정 전후에 6칸이 차면, 마지막에 깨어난 job은
  아무 로그 없이 `waiting`만 반복한다. 상태창에는 `waiting (stage=...)`로 보인다.
- 원인: pool 크기가 감싼 stage 수보다 작고, wrapper에 제출 시각·경과 시간 상한이 없다.
- 해결: (a) `max_workers`를 감싼 stage 수 이상으로, 또는 job별 전용 슬롯으로 두고 (b) wrapper가 제출
  시각을 기억해 stage 타임아웃을 넘기면 예외로 올려 stage를 실패시킨다. `pending`이 job 교체·run 변경
  뒤에도 남는 누수(키가 `(run_id, stage_id)`라 옛 run의 future가 회수되지 않음)도 같이 정리한다.
- 위험: 낮음~중간. worker를 늘리면 동시 subprocess가 늘어 로컬 자원 경쟁이 커진다.

- 위험: 낮음. 다만 OP2-02(worker 6칸)와 함께 고쳐야 큐 대기로 문제가 옮겨가지 않는다.

### [OP2-04] 정비 보류가 진입점 자체를 막지 않는다 — OS 서비스·직접 실행은 그대로 뜬다  [확정] [높음] [정확성]

- 위험: 낮음. 단 서비스가 1분마다 재시작을 시도하므로(Count=999) 거부 종료 코드가 로그를 채우지 않게

### [OP2-08] `emergency_stop --lockdown-env`만 쓰면 잠금이 성공해도 종료 코드 1·"종합 성공 False"  [확정] [중간] [정확성]

  commands/emergency_stop.py:124-145
- 증상: 프로세스를 죽이지 않고 잠금만 걸 때(`--lockdown-env`, `--kill` 없이) 잠금·상태 전이·.env 기록이

- 위험: 중간 — 발견 사항이 조용해지지 않도록 경보 경로를 반드시 함께 둬야 한다.

### [OP2-26] cron 판정이 1분마다 표현식을 다시 파싱한다  [확정] [낮음] [성능]
- 파일: monitoring/cron.py:164-186
- 증상: `fires_between`이 구간을 1분씩 훑으며 매번 `matches()`를 부르고, `matches`는 그 안에서
  `parse(expr)`로 5필드를 다시 집합으로 편다. 24시간 구간이면 표현식 하나당 1,440회 파싱이고,
  워크플로 36개 × cron 1~2개면 약 7~10만 회다.
- 근거:
  ```python
  def matches(expr: str, moment: datetime) -> bool:
      minute, hour, dom, month, dow = parse(expr)   # 루프 안에서 매번
  ```
  머리주석은 "판정 구간이 하루라 분 단위로 훑어도 1440회면 끝난다"라고 파싱 비용은 고려하지 않는다.
- 해결: `fires_between`이 `parse`를 한 번 하고 편 집합을 `matches`에 넘긴다(또는 `parse`에 캐시).
  hour/minute 집합을 먼저 검사해 날짜 순회를 줄일 수도 있다.
- 위험: 없음. heartbeat는 하루 한 번이라 체감 이득은 작다 — 함께 고칠 때만 한다.
